# Life Graph 鸿蒙全量迁移方案

日期：2026-10-21。状态：用户已审阅并授权按已实现功能范围开展迁移。此文保留设计基线及当时验证状态，当前实施结果见 ../../migration-progress.md；不表示全量迁移已验收完成。

## 1. 目标与已确认边界

用户已确认：以 LifeGraph-HW 为鸿蒙工程框架，覆盖原 life-graph-main 中已实现的功能；不迁移旧用户数据，作为新软件使用。原项目没有实现的登录认证、会员、账号绑定、云同步等单列，不在本轮补齐。

迁移完成的标准是：用户能够在鸿蒙设备上记录人物、关系、事件及媒体，浏览图谱，维护个人资料和主题，备份并恢复鸿蒙版自己的数据，并使用已有 AI 助手接口。界面预览、主机单测、编译、设备运行、正式签名分别留证，不能互相代替。

本次只修复已有试验的确认问题并制定方案，尚未开始下面的全量改写。

## 2. 本轮检查结论与当前可信基线

### 已确定的代码缺陷

1. 预览保护只依赖 `PeoplePage.previewOnly`。`@Preview` 包装组件会设置它，普通 `pages/Index` 页面预览不会，导致界面调用预览器 Mock 数据库后误报保存成功。
2. 保存通知原先在写 API resolve 后出现，没有校验刷新结果是否包含相同 ID、姓名、描述及更新时间的记录。
3. `onBackPress` 写在拆分后的普通组件里，没有由实际 `@Entry` 页面转发，不能据此保证系统返回键关闭编辑器。

DevEco 的本机日志直接证明第一个问题所处环境：预览路径是 `/pages/Index`，2026-10-21 20:32:26～20:32:31 的日志明确将 `getRdbStore`、`insert`、`querySql` 标记为 mocked implementation。它证明这次操作未走真实设备数据库；不能推断真实设备数据库本身一定有故障或一定正常。

### 本轮修正

- 真正的 EntryAbility 在启动时登记应用运行状态；未登记的页面预览与显式组件预览均进入只读预览模式。预览标记单独显示，打开表单也不清除。
- 保存后读取并核对人物记录，删除后核对记录不在活跃列表。失败时不报成功，提示结果待确认；退出可重复提交的新建表单，刷新不重发写操作。
- 由 Index 的 `onBackPress` 转交页面控制器，组件离开时清理回调。

该运行状态是单 UIAbility 原型的保护，不是通用环境检测 API。未来若增加 Ability 或多窗口，应由运行时容器替代静态开关。不能宣称已在所有预览器版本中实测通过。

## 3. 推荐技术路线与实现者决定

以下是方案建议，不把它们描述成用户已逐项同意的决定。

- 使用 ArkTS + ArkUI 构建原生界面，Stage UIAbility 管理应用生命周期；不引入 RNOH、Expo 或 React 运行时。
- 图谱第一版使用 ArkWeb 承载本地离线 D3/SVG。保留图谱布局与交互脚本，替换 RN 消息桥。列表、表单、弹窗、设置、媒体操作均为鸿蒙原生。图谱的 Web 部分是明确的混合实现，不称作纯原生绘图。
- 先交付手机端完整闭环；现有工程声明的 tablet、2in1 保留并做基本布局检查，但专门的大屏工作台、多窗口、跨设备流转不作为本轮验收目标。
- 保持现有目标 SDK 26.0.0、兼容版本 6.1.0(23)，直到设备基线实测通过；若目标设备低于此版本，先明确调整兼容范围并重新检查 API。
- 延续原应用的主题、布局语义与中文文案；不将迁移同时扩大为产品重设计。
- 先使用单个本地工作空间与“我”节点，保留 AccountId 和工作空间边界。没有可用认证服务时不添加虚假登录成功或不可用的强制登录。

若用户要求图谱也全部原生绘制，应单独估算布局算法、Canvas 绘制、命中检测、文字和头像布局、手势及性能，不在此方案工期内默认包含。

| 个人资料和统计 | 名称、头像、简介／生日等实际字段、人数事件数、空间占用 | 模型和配置同步，跨重启一致 |
| 外观设置 | 主题、明暗模式、自定义事件颜色等实际配置 | 单次操作后界面与选项一致，重启恢复 |
| 本地备份 | 导出鸿蒙版 ZIP、预览清单、导入恢复、自有格式版本 | 包含媒体、关系及配置；失败可恢复 |
| AI 助手 | 接入现有聊天 API、本地查询工具、多轮工具结果、文本展示 | 真服务联调与 Mock 分开，断网／超时可恢复 |

“首次为空”指不自动插入原工程的演示人物、演示关系及演示事件。允许初始化内部“我”节点和关系／情绪／分支等默认可选项。原 `applyAccountSeed` 当前同时灌入演示数据，不能直接复制其运行路径；预览夹具另放。

原文档与源码有差异，例如种子数据已采用自然键去重，不能只依赖旧 ADR 中的 seedVersion 描述。实现前按当前服务和测试逐项建立对应表。

事件人物图在原 ADR 中标注 reserved；分支点击 zoom-to-node、AI 整理按钮也仍有 TODO。对这些入口保留已实现部分，不把预留效果当成现有功能已经迁移。

## 6. 目标架构与数据设计

建议目录按职责组织，具体文件名可由实现者决定：

```text
entry/src/main/ets/
  application/    启动、运行时、生命周期、导航装配
  domain/         实体、值对象、错误、Repository 与能力接口
  features/       业务服务、页面状态、用例及 DTO
  data/           RDB、事务、配置、文件、网络实现
  pages/          ArkUI 页面与 NavDestination
  components/     可复用原生组件
  preview/        显式、只读、无生产写入的预览夹具
entry/src/main/resources/rawfile/graph/
                  本地图谱 HTML、D3 和桥接脚本
```

依赖方向：页面调用用例／页面状态，业务依赖领域接口，数据层实现接口，应用启动统一装配。全量阶段把试验中页面直接创建 Repository 的方式收回运行时层，不在每个页面复制数据库连接。

### 数据库

- 业务保留 11 张表：persons、relations、person_relations、events、event_persons、branches、event_branches、emotions、event_emotions、media_assets、event_assets。
- 保留毫秒时间戳、稳定 ID、软删除、外键、必要索引和活跃记录唯一约束。人物与关系等的具体去重语义以当前原服务／测试为准，不能统一简化成姓名唯一。
- 本地工作空间身份、资料和设置由应用元信息／类型化配置负责；没有服务端认证时，不必为 backend_users、local_account_bindings 的占位链路制造数据。为未来工作空间隔离预留接口，认证相关表待实际需要时迁移加入。
- AppRuntime 持有数据库；业务事务按连接串行调度，避免页面各自开库和事务跨连接失效。前后台不随意销毁连接，关闭／切换必须等待在途操作结束。
- 版本迁移显式按版本执行，只在成功后更新版本，不在每次启动时强行把 `version` 写成 1。
- `lifegraph-native-spike.db` 是原型库；正式版另建版本化库。原型不承诺作为正式用户数据自动导入，也不在升级安装时静默删除它；正式包名在发布前确定。

### 文件与事务

- 数据库仅保存媒体相对路径，绝对沙箱路径在读取时解析，不把选择器临时 URI 当作永久文件。
- 图片／语音先复制到临时区、校验可读性，再提交数据库关联，最后完成文件落位。数据库与文件不是同一事务，必须记录操作阶段并提供失败补偿／启动清理。
- 配置写入失败不能显示整体保存成功；主题等高频设置采用可追踪的持久化结果与回滚／重试策略。
- 自有备份恢复先解压验证至临时工作空间，再导入新库、校验关联与媒体，最后切换当前工作空间；失败保留原数据。校验路径、版本、文件数量与体积边界，避免直接清空活跃库再导入。

| 当前技术 | 鸿蒙替代方向 | 首次验证 |
|---|---|---|

| RN WebView | ArkWeb＋受限 JS 桥 | 消息往返、离线 D3、本地头像、恢复重发 |

具体 API 名称与最低版本在对应能力试验中按已安装 SDK 验证；上表不表示第三方库或全部 API 已实测适配。

## 8. 图谱与 AI 的专门约束

图谱 JSON 由原生服务组装，ArkWeb 只承担图形展示和手势。桥接只允许 ready、人物点击、事件点击、缩放等已定义消息，校验消息类型与 ID，页面离开后丢弃旧回调。Web 就绪前缓存最新数据，重载后重新发送；头像由受控资源映射加载，避免每次刷新传输大量原图 Base64。图谱页面不得通过桥接任意执行数据库操作。

图谱技术试验前移：验证 50、200、500 节点及相应关系边的代表性数据，记录首屏时间、拖动／缩放响应、内存与恢复表现。这是测量分档，不是对原应用最大数据规模的承诺；目标数据规模见待确认项。

AI 后端保留 FastAPI 服务与 `/api/v1/ai/chat` 协议；客户端迁移现有 11 个本地查询工具，保留当前最多 5 轮工具执行的限制。模型密钥仍只放服务端。Mock provider 和真实服务联调分别标记，收到 Mock 文本不算 AI 端到端通过。对超时、断网、页面退出、工具参数非法、模型返回无效结构分别处理，不将整库默认上传。

工期为一名熟悉 ArkTS 和原业务的工程师的投入估计，单位为人周；不等于 AI 实际运行时间，也不保证日历交付日。各阶段保留可运行版本。

不将原型的数百行代码按比例外推为全部项目的准确工期；P0 设备结果和图谱试验完成后更新估计。

## 10. 验证与验收规则

1. 编译：每个可运行里程碑构建 HAP，留工具版本、结果和产物；unsigned 不等于可安装。
2. 业务：以原项目 Service 测试的业务语义建立迁移对照，重点覆盖关系强度、唯一性、软删除和关联处理。
3. 原生数据：使用设备侧测试验证真实 RDB 与文件 API，不以 Node 测试或 Mock 预览代替。
4. 用户流程：从干净安装开始，人物、关系、事件、媒体、图谱、设置、备份、AI 完整走通。
5. 持久化：至少包含页面离开、强制停止应用再启动、设备重启；对设置、文本、媒体分别验证。
6. 故障：写入失败、读回失败、录音中断、取消选文件、空间不足、备份损坏、网络超时，均检查无虚假成功与无重复提交。
7. 布局：核对截图、键盘遮挡、系统安全区、字体放大、长内容、空列表及加载错误。
8. 预览：组件与普通页面入口都明确展示只读模式；预览 API Mock 的返回不能驱动生产成功提示。

## 11. 外部条件与当前假设

- 用户负责提供可用的本地模拟器或真机与开发者签名条件；可由代理在工具可访问时执行测试，否则提供明确的人工步骤和截图／日志要求。截图用于布局验收；数据持久化需要实际操作记录。
- AI 使用现有后端服务；服务部署地址、可访问网络和真实 provider 可用性需要联调时确认，不能沿用手机 localhost 调试地址。
- 建议暂以普通手机、200 节点左右的日常图谱为主要体验目标，并测试到 500 节点观察退化；这是待真实使用规模校准的规划假设，不是用户需求。
- 发布商店和组织签名身份、正式 bundleName、隐私声明由发布前提供；本方案只估算准备可签名交付物和完成配置后的安装验证，不承诺商店审核时长。
- 若当前只有 Preview，可继续业务层实现、主机逻辑测试和编译；所有设备依赖项保留“待验证”，P0 设备验收关口不视为完成。

实现者可决定：目录细分、组件拆分、SQL 封装方式、测试命名、压缩库在能力试验后的选择。不得自行把未实现的账号／会员／云同步加入本轮，或把纯原生图谱和专用大屏支持当作已约定目标。
