## 2026-10-21 代码初查（未改动功能）

- 两项都涉及 NativeApp.ets 的 personEditor：关系列表 ForEach 使用数组下标作 key；updateRelation 每次替换关系对象，但行内显示及回调捕获 input。需要核对同 key 下行的刷新与旧对象闭包，存在显示未更新、后一次操作用旧值覆盖新选择的嫌疑；这是排查假设，不是已证实根因。
- 新增关系默认对象确实为“我”，但 savePerson／writeEdge 按传入的 targetPersonId 保存，并未发现业务层将任意对象强制改成“我”的代码。现有服务层测试不能覆盖原生 Select／Slider 的状态与回调问题。
- 后续验收至少包含：拖动强度立即显示；选 B 后修改类型／强度并保存仍关联 B；只选 B 不动滑条；多行分别选 B／C；移除首行后编辑剩余行；重开编辑器及数据库端点核对。普通 UI 缺陷可暂缓，关系对象错误应在全量验收前关闭。

以下是验证缺口，暂不归为已复现缺陷：大图与录音权限／中断、设备重启、备份原生往返、真实 AI、较大图谱性能。详见 migration-progress.md。

## 本轮修复

根因：ForEach 按数组下标复用旧行；updateRelation 替换普通对象后，旧行文本及回调仍引用旧 input。Slider 自身可显示新值、数据库也能收到新强度，但旁边 Text 没有可靠的观察依赖；选择人物之后再改类型／强度，还会把捕获的旧 targetPersonId 写回。移除前一行后，下标复用也有串行风险。

- 关系表单改为稳定行 ID 的 RelationEditorItem，使用 @Observed；独立 RelationEditorRow 通过 @ObjectLink 观察当前行。
- 选人、选类型、调强度仅修改当前对象的对应字段；回调不再带回其他字段的旧快照。
- 两个 Select 的 selected 索引和展示值均绑定当前 ID；保存时从各行复制独立的 RelationInput，UI 行 ID 不写数据库。
- 按稳定行 ID 删除，新增不会复用删除行的身份；保存期间禁用行控件。
- 不猜测并自动改写用户原来已经保存错误的关系对象；这些记录需要用户重新选择正确人物并保存。

回归脚本：scripts/test-relations-ui.py，使用鸿蒙 SDK uitest 操作实际应用和数据库。检查连续拖动 5→1→5、选人后改类型／强度、两行分别保存、强制停止重开、删除首行后编辑次行、增加移除行、重开编辑器及临时人物清理。UI 布局证据保留本机 evidence/relations-*.json，不进入版本控制。

验证结果：主程序构建通过并覆盖安装到模拟器；34 项主机回归通过；上述脚本完整重跑后 8 个实际界面检查点全部通过、退出码 0（见 evidence/relations-ui-test.log 与 relations-ui-summary.json）。首轮在清理阶段因脚本将系统弹窗 Text 当成 Button 而中断，已修正脚本并完整重跑；两轮临时人物和复现人物 LG_REL_BEFORE 均已清理，原有三位人物仍在。
